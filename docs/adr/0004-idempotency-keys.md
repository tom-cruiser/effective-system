# ADR 0004: Idempotency keys stored on the ledger transaction

- Status: Accepted
- Date: 2026-11-04

## Context

Mobile networks drop responses. A rider's app that times out on "pay for ride" cannot know
whether the payment happened. If it retries blindly, the rider may pay twice. If it does not
retry, the payment may be lost. Payment providers' webhooks are also delivered at least once.

## Decision

- Every money-moving endpoint requires an `Idempotency-Key` header (1–100 characters, typically a
  UUID generated by the client per logical operation).
- The key is stored **in the `ledger_transactions` row itself**, under `UNIQUE (idempotency_key)`,
  together with `request_hash`. It is written in the same database transaction as the postings.
  This means the key and the money movement exist together or not at all. A separate idempotency
  table could leave "key recorded, money not moved" or the reverse.
- `request_hash` is the SHA-256 of:
  - the operation name (`top-up`, `transfer`, `reversal:<id>`, …), plus
  - the request re-serialised as JSON.

  Formatting differences (whitespace, key order) do not count as a different body. The same key
  reused on a different endpoint does.
- Outcomes:
  - **New key**: the transaction is executed and returns `201 Created`.
  - **Same key, same hash**: the original transaction is returned with `200 OK`. Nothing is posted
    again, even if balances have since changed.
  - **Same key, different hash**: `409 IDEMPOTENCY_CONFLICT`.
- **Concurrent duplicates.** Two identical requests can both miss the initial lookup. The loser
  then fails, either on the unique constraint or on a business rule (e.g. the winner already spent
  the money). `TransactionService` catches that failure and looks the key up again, so the loser
  also receives the winner's transaction. `IdempotencyApiIT` fires ten identical "spend everything"
  requests at once. The result is one `201`, nine `200`s with the same id, and one set of postings.
- Failed requests (e.g. `INSUFFICIENT_FUNDS`) store nothing. Retrying the same key after topping
  up therefore succeeds, which matches what a user expects.

## Consequences

- Keys are global, not per client. In this demo a key collision between two users would show up as
  a conflict. A multi-tenant version would make the unique constraint `(owner, key)`.
- Keys never expire, because ledger rows are kept forever (ADR 0003). That is acceptable here.
  At high volume one would keep keys in a separate table with a time-to-live and an index.
- Read endpoints and account creation are not covered. Account creation is not money movement,
  and a duplicate creates an empty wallet that can be ignored.
